# `fix/hash-collapse-anti-shift` 分支工作总结

## 1. 分支目标

本分支主要围绕音乐相似度检索系统中的**深度哈希空间坍塌问题**展开，目标是让模型输出的 128-bit 音频哈希真正具备区分能力，避免不同歌曲被编码成相同或极近的二进制码，从而提升 Faiss 汉明距离检索的可靠性。

分支最终选择 `v2` 方案作为生产/论文主方案：

- 当前模型：`./checkpoints/hash_model_v2_epoch_10_best.pth`
- 当前索引：`music_hash.index`
- 当前索引规模：`203200` 条 128-bit 子指纹
- 当前服务：FastAPI 后端加载 v2 模型与 v2 Faiss 索引

---

## 2. 问题背景：哈希空间坍塌

原始模型虽然可以在业务层搜索中命中部分结果，但底层哈希空间存在明显坍塌风险：

- 不同歌曲之间可能出现大量极低汉明距离；
- 部分不同歌曲子指纹甚至出现 `0 bit` 距离；
- 若继续扩大曲库，误检风险会迅速放大；
- 业务命中依赖多窗口与候选合并，底层哈希质量不足。

因此，本分支没有只看 Top-1 命中率，而是新增了专门的哈希健康诊断指标体系。

---

## 3. 新增诊断与评估工具

### 3.1 哈希坍塌诊断脚本

新增：`evaluate_collapse.py`

该脚本用于评估全库哈希空间健康度，核心指标包括：

- **bit-balance**：每一位 0/1 是否均衡；
- **uniqueness**：全库哈希码唯一率；
- **collision**：跨歌曲完全碰撞码数量；
- **same-song distance**：同一首歌不同窗口之间的汉明距离；
- **cross-song distance**：不同歌曲之间的汉明距离。

该脚本成为后续 v1/v2/v3 对比实验的主要量化依据。

### 3.2 最优 epoch 选择脚本

升级：`select_best_epoch.py`

主要改动：

- 支持 `--prefix` 参数；
- 可以在多版本 checkpoint 并存时选择指定版本的最佳 epoch；
- 支持 v1、v2、v3 多路线实验复用。

### 3.3 业务层端到端测试脚本

新增：`tools/e2e_search_test.py`

用途：

- 从训练集/曲库中随机抽样音频；
- 通过 FastAPI `/search` 接口真实上传查询；
- 统计 Top-1、Top-5 命中率和平均响应时间；
- 验证底层哈希指标改进不会破坏业务层检索效果。

## 4. 训练与模型侧主要改动

### 4.1 数据集构造增强

修改：`dataset.py`

主要改动：

- 将正样本从“原始音频加少量白噪声”升级为**同曲不同时间片段**；
- 使用 30 秒音频缓存，支持从同一首歌内采样不同 5 秒窗口；
- 增加数据增强策略，包括随机增益、白噪声、SpecAugment 等；
- v2 以后保持 anchor 不增强，使训练分布更接近真实查询分布。

意义：模型不再只学习“几乎相同波形”的微小扰动，而是学习同一首歌不同片段之间的稳定相似性。

### 4.2 模型输出支持 beta-tanh 退火

修改：`model.py`

主要改动：

- 将最终 `Tanh` 从固定层中拆出；
- 在 `forward` 中加入 `beta` 参数；
- 训练时逐步增大 beta，使连续输出逐渐逼近二值符号函数；
- 推理时保持默认 `beta=1.0`，兼容原有调用方式。

意义：在保持可微训练的同时，逐步增强哈希二值化稳定性。

### 4.3 训练损失函数升级

修改：`train.py`

本分支将训练目标从单一 Triplet Loss 升级为复合目标：

- **easy triplet loss**：常规 anchor-positive-negative 约束；
- **hard negative mining**：在 batch 内构造更难负样本；
- **quantization loss**：推动输出接近 `-1/+1`；
- **bit-balance loss**：推动每个 bit 在 batch 内接近 0/1 均衡；
- **CosineAnnealingLR**：平滑学习率衰减；
- **实时健康指标**：训练过程中监控同曲距离与 bit 偏移。

意义：训练目标从“拉近同曲、推远异曲”扩展为“同时保证二值码可量化、可分散、不卡死”。

### 4.4 训练环境隔离

新增：`requirements-train.txt`

用途：

- 将 GPU 训练依赖与生产服务依赖拆开；
- 指定 CUDA 版本 PyTorch；
- 避免污染轻量 FastAPI 生产运行环境。

## 6. 相比主分支 v1 的具体改进

本分支的核心价值不是简单“换了一个模型”，而是从**训练数据构造、损失函数、哈希健康诊断、索引重建、业务验证和前端可解释性**多个层面，对原本主分支 v1 方案进行了系统性增强。

### 6.1 训练目标从“能命中”升级为“码空间健康”

主分支 v1 更关注业务层 Top-1 命中效果，但底层哈希码存在坍塌风险。本分支 v2 将目标扩展为：

- 同曲窗口之间保持较小汉明距离；
- 跨曲窗口之间尽量接近 128-bit 随机码的理论期望距离 `64 bits`；
- 每一位 bit 尽量保持 0/1 均衡；
- 减少不同歌曲共享完全相同哈希码的情况；
- 避免出现死位和大规模 `0 bit` 跨歌碰撞。

换句话说，v1 更像是“业务能搜到”，v2 则进一步要求“哈希空间本身是可靠的”。

### 6.2 模型训练策略改进

| 维度 | 主分支 v1 | 本分支 v2 改进 |
|---|---|---|
| 正样本构造 | 原始片段加弱白噪声，变化较小 | 同一首歌内不同时间窗口，学习真实同曲不变性 |
| 数据增强 | 较弱 | 随机增益、白噪声、SpecAugment 等增强 |
| Anchor 处理 | 与增强样本混合较多 | v2 保持 anchor 不增强，更接近真实查询分布 |
| 损失函数 | 以 Triplet Loss 为主 | Triplet + hard negative + quantization + bit-balance |
| 难负样本 | 依赖随机负样本 | batch 内 hard negative mining |
| 二值化稳定性 | 缺少显式约束 | beta-tanh 退火 + quantization loss |
| bit 均衡 | 缺少足够约束 | 强化 bit-balance loss，防止死位与偏置 |
| 训练监控 | 主要看 loss | 增加同曲距离、bit 偏移等健康指标 |

### 6.3 哈希空间质量改进

| 指标 | 主分支 v1 | 本分支 v2 | 改进意义 |
|---|---:|---:|---|
| same-song mean | `13.83 bits` | `16.92 bits` | v1 同曲更紧，但 v2 仍处于可接受范围 |
| cross-song mean | `53.20 bits` | `61.65 bits` | v2 明显更接近理论期望 `64 bits` |
| 区分带宽 | `39.37 bits` | `44.73 bits` | 同曲/跨曲距离分离更明显 |
| uniqueness | `88.70%` | `94.85%` | 全库哈希码唯一率显著提升 |
| 跨歌碰撞码数 | `1886` | `706` | 不同歌曲完全撞码显著减少 |
| bit-dev mean | `0.149` | `0.0789` | bit 分布更均衡 |
| 死位数量 | `5 个` | `0 个` | 消除 bit 长期固定失效问题 |
| 抽样跨歌 distance=0 | 存在风险 | `0` | 大规模 0-bit 坍塌未复现 |

其中最关键的是 `cross-song mean` 从 `53.20 bits` 提升到 `61.65 bits`。对于 128-bit 哈希而言，不相关样本之间的理论平均汉明距离约为：

```text
128 / 2 = 64 bits
```

v2 的 `61.65 bits` 已经非常接近该理论值，说明不同歌曲的哈希码被有效拉开。

### 6.4 业务层效果没有牺牲

虽然 v2 不再一味追求同曲距离最小，而是更重视整体码空间健康，但业务层效果仍然保持稳定：

| 指标 | v2 最终结果 |
|---|---:|
| Top-1 | `10/10 = 100%` |
| Top-5 | `10/10 = 100%` |
| 平均响应时间 | `9367 ms` |

这说明 v2 并不是用业务准确率换取码空间健康，而是在保持业务命中的同时，提高了底层检索结构的可扩展性和可靠性。

### 6.5 工程与可复现实验能力改进

相比主分支，本分支还补齐了多项工程能力：

- 新增 `evaluate_collapse.py`，可以全量诊断哈希空间坍塌；
- 新增/升级 `select_best_epoch.py`，支持多版本 checkpoint 选优；
- 新增 `tools/e2e_search_test.py`，支持真实 API 端到端测试；
- 新增 `requirements-train.txt`，区分训练环境和生产环境；
- 新增 `rebuild_songs_db.py`，保证 Faiss 索引与 SQLite 映射一致；
- 更新 `index.html`，在前端直接展示汉明距离；
- 用文档记录 v1/v2/v3 消融实验，方便论文复现和答辩展示。

### 6.6 一句话总结

相较于主分支 v1，本分支 v2 最大的改进是：**从“搜索结果看起来能用”提升为“底层 128-bit 哈希空间可解释、可诊断、可扩展、低碰撞”，显著缓解了不同歌曲汉明距离过近甚至 0-bit 撞码的问题。**

## 7. v1/v2/v3 实验结论

### 7.1 v1：同曲更紧，但码空间仍不健康

v1 方案显著改善了同曲聚合能力，但存在以下问题：

- bit-balance 偏移仍偏大；
- 有死位；
- 跨歌碰撞仍较多；
- 跨歌距离未充分接近 128-bit 随机码理论期望。

结论：v1 适合作为“紧同曲路线”对照组，但不适合作为最终方案。

### 7.2 v2：最终生产/论文主方案

v2 通过更强的 bit-balance 约束、hard negative mining、量化损失和更合理的数据增强，取得当前最佳综合结果。

最终 v2 全量诊断结果：

| 指标 | v2 最终结果 |
|---|---:|
| 索引子指纹数量 | `203200` |
| bit-balance mean\|p-0.5\| | `0.0789` |
| bit-balance max\|p-0.5\| | `0.2455` |
| uniqueness | `94.85%` |
| 跨歌碰撞码数 | `706` |
| same-song mean | `16.92 bits` |
| cross-song mean | `61.65 bits` |
| cross-song distance=0 抽样命中 | `0` |

业务层 e2e 结果：

| 指标 | 结果 |
|---|---:|
| Top-1 | `10/10 = 100%` |
| Top-5 | `10/10 = 100%` |
| 平均响应时间 | `9367 ms` |

结论：v2 能够显著拉开不同歌曲之间的汉明距离，跨歌平均距离接近 128-bit 随机码理论期望 `64 bits`，同时保持业务层检索命中率。

### 7.3 v3：中间路线消融实验

v3 试图采用介于 v1 和 v2 之间的中间超参数配置，验证是否存在更平滑的折中点。

实验结论：

- v3 业务层仍可保持较好表现；
- 但哈希空间健康度不如 v2；
- bit-balance 不是简单线性可调指标，而更接近“硬阈值”现象；
- 若约束不足，死位和碰撞会复发；
- 因此最终不采用 v3 作为生产方案。

## 9. 额外实测：5 首不同歌曲汉明距离

为直观验证 v2 是否仍存在跨歌 `0 bit` 问题，本分支额外从库中随机抽取 5 首不同歌曲，各取一个子指纹，计算两两汉明距离。

抽样结果：

| 对比 | 汉明距离 |
|---|---:|
| YEIZON ↔ zero rhythm dollar boy | `46 bits` |
| YEIZON ↔ La Fin Du Monde | `80 bits` |
| YEIZON ↔ Footsteps | `86 bits` |
| YEIZON ↔ Chacha Dub | `36 bits` |
| zero rhythm dollar boy ↔ La Fin Du Monde | `58 bits` |
| zero rhythm dollar boy ↔ Footsteps | `72 bits` |
| zero rhythm dollar boy ↔ Chacha Dub | `50 bits` |
| La Fin Du Monde ↔ Footsteps | `40 bits` |
| La Fin Du Monde ↔ Chacha Dub | `72 bits` |
| Footsteps ↔ Chacha Dub | `74 bits` |

汇总：

```text
n_pairs = 10
min     = 36 bits
max     = 86 bits
mean    = 61.40 bits
zeros   = 0
```

结论：随机 5 首不同歌曲之间没有出现 `0 bit` 汉明距离，平均距离 `61.40 bits`，与 v2 全量诊断中的跨歌平均 `61.65 bits` 高度一致。
