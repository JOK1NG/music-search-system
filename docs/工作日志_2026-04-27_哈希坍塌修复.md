## 1. 起因 — 为什么要修

### 1.1 问题暴露

旧版模型 (`hash_model_epoch_3.pth`) 训练时所用 triplet 正样本仅 = anchor + 0.01 高斯白噪。
线下扫描发现：

- 不同歌曲产生 **完全相同的 128-bit 哈希码** ——典型的 **哈希空间坍塌（Hash Space Collapse）**
- 5 个比特长期固定（dead bits），有效熵不足 123 bit
- 跨歌曲汉明距离均值仅 36 bit（理想 64 bit），码本"挤成一团"

### 1.2 根因猜测（待诊断验证）

1. 正样本扰动太弱（白噪 0.01）→ 模型只需"复制 anchor"即可打 0 损失
2. anchor 与 positive 的 mel-spec 几乎一致 → 学不出"同曲不变性"
3. 没有 quantization loss / bit-balance loss → tanh 输出乱漂、bit 不均衡
4. 训练 epoch 不足 + lr=1e-5 太保守 → 没收敛到泛化点

## 2. 工作流程（按时间顺序）

### Step 1 — 写诊断脚本（read-only 优先）

新增 `evaluate_collapse.py`，五维定量诊断：

- **[A] bit-balance**：每位为 1 的概率距 0.5 的偏差（理想 0）
- **[B] uniqueness**：唯一码数 / 总码数（理想 100%）
- **[C] collision multiplicity**：同码出现次数分布、最严重一码"撞了几首歌"
- **[D] same-song Hamming**：同曲多窗口码间距离（理想 < 10）
- **[E] cross-song Hamming**：跨曲码间距离（理想接近 64）

跑旧模型基线，铁证如下：

```
[A] bit-dev mean=0.10  max=0.50（5 个死位）
[B] uniqueness=59.94%
[C] 跨歌碰撞码=14030，最严重一码撞 413 首歌
[D] same=16.79
[E] cross=60.39
```

→ 锁定 5 个死位是首要矛盾，码空间坍塌不是猜测而是事实。

### Step 2 — 切分支 + 设计修复路线

```
git checkout -b fix/hash-collapse-anti-shift
```

写下 5 个治疗手段（5 颗药丸一起吃）：

1. **数据侧**：同曲不同窗口（time-shift positives, 5s 起点随机）+ SpecAugment + 随机增益
2. **模型侧**：tanh 改成 `tanh(β·z)`，β 训练时退火 1.0 → 4.0/10.0，逼近 sign 又保留可微
3. **损失侧**：triplet + 量化损失 (`(|h|-1)²`) + 位平衡损失 (`mean(h)²`)
4. **采样侧**：在线 hard negative mining（batch 内重排）
5. **训练侧**：lr 1e-5 → 1e-4，CosineAnnealingLR，epoch 3 → 15/10

### Step 3 — 配套基础设施

并行做了几件不写在论文但很重要的工程改造：

- 把 `precompute_cache.py` 升级到 30s 缓存（训练才能在中段随机抽 5s 起点）
- 把 `batch_health_metrics()` 在训练日志中实时打印同曲距 + bit-dev，**不再瞎训**

## 5. 答辩 Q&A 备忘

### Q1: 为什么坚持 128 bit 而不是 64 bit？

128 bit 的存储成本只是 64 bit 的两倍（在百万级码本上仍是 16 MB 量级），但容量是 2^128 而非 2^64，
**留了足够空间应对未来千万级 → 亿级码库**，且用 IndexBinaryFlat 时检索速度对位长度近线性，不构成瓶颈。
此外 64 bit 在 ESC-50 这种小集合是平衡点，但本项目 8000 首已开始触碰 64 bit 的容量天花板。

### Q2: 如何证明你修好了哈希坍塌？

三组数据：

1. **碰撞码数从 14030 → 706（−95%）**
2. **死位 5 个 → 0 个**
3. **uniqueness 59.94% → 94.85%**

且业务层 Top-1 从未掉过 100%（同 seed 抽样可复现）。

### Q3: v1 和 v2 都达到 Top-1 100%，为什么选 v2？

业务层在 5 秒窗口 + 多窗口投票下对 13~17 bit 的同曲距差不敏感，
但 **论文的核心命题是码空间健康度**，v2 在五大指标上四胜一负，
特别是消灭了 v1 无法解决的 **5 个死位**（信息熵真实损失）。

### Q4: 为什么 same-song Hamming 反而比 v1 大？

这是有意为之的 trade-off。v1 通过紧 margin + 重 anchor 增强让 anchor/positive 几乎重合，
同曲距虚低但代价是码空间被压扁；v2 放松同曲约束、加重位平衡，让模型学**真正的同曲不变性**而非记忆。
体现在 cross-song 从 53.20 (v1) → 61.65 (v2)，**区分带宽**（cross−same）从 39.4 → 44.7。

### Q5: 训练时间 / 资源？

- 单卡 RTX 4080 16GB
- v1 训 ~2h（15 epoch），v2 训 ~1.5h（10 epoch）
- 30s 波形缓存 ~3GB，加速一次 epoch 从 ~30 min 降到 ~9 min

### Q6: 服务器部署影响？

零影响。生产服务器走 Dockerfile + 本地 `wheels/` 离线装包，根本不读 `requirements.txt`。
GPU 训练依赖单独放在 `requirements-train.txt`，仅本地用。

### 8.4 v3 的关键发现：中间调优 ≠ 自动折中

**v3 反直觉结论**：

- ✅ same_mean **15.98** 确实介于 v1 (13.83) 与 v2 (16.92) 中间
- ✅ cross_mean **59.66** 确实介于 v1 (53.20) 与 v2 (61.65) 中间
- ❌ **bit_dev max 0.497 退化回接近 v1 水平 —— 1~2 个死位重新出现**（bit 79 漂到 99.7%、bit 40 漂到 96.2%）
- ❌ **uniqueness 92.91% 反而比 v2 低 1.94 个百分点**（因为死位复发压缩了码空间）
- ❌ **碰撞码数 1104 比 v2 多 56%**

**根因诊断**：`LAMBDA_BAL=0.10` 压不住 bit 漂移。位平衡损失和位死位是一个**硬阈值问题**——必须达到 0.15 才能完全消灭死位，0.10 是"半死不活的中间态"，比 0.05 好、但比 0.15 明显差。

### 8.5 论文三路消融结论（可直接写进方法论章节）

> 我们设计了三套超参配置作为消融实验：
>
> 1. **v1 路线**：小 λ_bal + 大 margin + anchor 增强 → **紧贴同曲**（same=13.83）但码空间收缩（cross=53.20, 5 死位）
> 2. **v2 路线**：大 λ_bal + 小 margin + anchor 不增强 → **撑开码空间**（cross=61.65, 零死位）但同曲贴合度下降（same=16.92）
> 3. **v3 路线**：算术中间值 → **同曲/码空间指标都只居中**，同时死位复发，证明 bit-balance 是**硬阈值现象**而非线性可调
>
> 三路在 5s 滑窗 + 多窗口投票的业务层均达到 100% Top-1，说明论文关注的码空间健康度与末端业务表现之间存在**缓冲带**；但在大规模码本（> 100k 首）下 v2 的 44.7 bit 区分带宽具有更强的可扩展性。因此系统采纳 v2 作为最终部署。
